<result>I've ranked the techniques below by expected impact on your setup. Every number comes from the cited source; anything I couldn't confirm is marked. One piece of arithmetic drives most of the ranking: Sonnet cache reads cost $0.30/MTok, so your ~$1.2 is roughly 3–4M cache-read tokens (about 55 turns × 60k average context). Cost grows with turns × context size, so the biggest wins come from making context smaller where it's born and from splitting it up. Trimming wording helps much less.

## 1. Keep tool results small from the start, with a handle to fetch the full page again (highest impact)

**Summary.** Manus drops bulky page or document content from context but keeps a URL or file path so it can be fetched again ("restorable compression"). It treats the file system as memory and the KV-cache hit rate as its main production metric. Its input:output ratio is about 100:1, and cached Sonnet input is 10× cheaper. Browser Use's `extract` tool runs a separate call over the page markdown and returns only the answer instead of loading 20k+ token pages into the agent's context. AgentOccam's observation simplification (removing redundant elements, Markdown restructuring) plus action-space pruning took WebArena from 16.5% (plain agent) to 43.1%. Its paper gives no clean per-component gain for observation alone; the per-step breakdown is only in a figure. Prune4Web pre-filters the DOM in code: 25–50× fewer candidate elements, and grounding accuracy went from 46.8% to 88.3%.

**Sources:** https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus · https://browser-use.com/posts/speed-matters · https://arxiv.org/abs/2410.13825 · https://ojs.aaai.org/index.php/AAAI/article/view/40772/44733

**Apply.** Each MCP page tool keeps the full page text on the server under a handle and returns only a compact outline: headings, interactive elements with short IDs, table headers with row counts, and the first N rows. Add `page_find(handle, query)` and `page_rows(handle, range)` so the model can pull specific spans. In the Claude Code CLI you can't remove a tool result after it's in history, so the result has to be small when it's first returned. **Estimate:** average context down 40–60%, cost down 35–50%. The model still chooses what to read, which stays within the fair-play rules.

## 2. One parallel subagent per site, writing results to files

**Summary.** Anthropic's research system has a lead agent plus 3–5 parallel subagents, each also calling tools in parallel. It reports up to 90% less research time and +90.2% on its internal eval versus a single agent. Subagents write their output to storage and pass back references, which avoids a "game of telephone" through the conversation. Token usage alone explained 80% of the performance variance on BrowseComp. The catch: about 15× the tokens of a chat, and a poor fit when tasks share context or depend heavily on each other.

**Source:** https://www.anthropic.com/engineering/multi-agent-research-system

**Apply.** Because cost scales with turns × context, four subagents of about 14 turns each over separate small contexts cost much less in cache reads than one 55-turn context. Wall-clock time becomes roughly the slowest site instead of the sum of all four. A short planner turn first collects the cross-site keys (tender ID, material numbers) and hands them to each subagent. Each subagent adds about 10–20k tokens of startup context (third-party estimate, unverified), so keep subagent prompts lean. **Estimate:** 40–60% less time, 20–40% less cost. Risk: a fact that only shows up on another site (for example, an email that changes a quantity). Handle it with an explicit reconciliation step.

## 3. Stop generating the 12k-token final JSON

**Summary.** Browser Use measured output tokens at about 215× the time cost of input tokens (10 output tokens ≈ 62.6 ms; 1k input tokens ≈ 29.1 ms). They kept actions to 10–15 tokens. YAML or tabular formats save about 20–35% of tokens versus JSON. That comes from mixed-quality sources, and gains are small for short outputs.

**Sources:** https://browser-use.com/posts/speed-matters · https://arxiv.org/pdf/2602.00887

**Apply, in order of payoff:**
- **(a) Record facts by pointer.** `record(field_path, handle, span_id)`: code copies the exact text from the stored page, normalizes numbers and dates, and builds the final JSON plus the form fill. The model emits a few tokens per fact, and each value is verbatim by construction.
- **(b) Record facts as they're found.** If you don't use pointers, record each fact during exploration so the output is spread across turns, or emitted concurrently by the subagents in #2.
- **(c) Compact keys and TSV** for whatever the model must still write.

**Estimate:** saves about 60 of the 70 seconds at the end. This also feeds the reliability work in #6.

## 4. Fewer turns: macro actions, parallel calls, better tool descriptions

**Summary.** When Anthropic rewrote its tool descriptions using an agent that tested the tools, later agents finished tasks 40% faster. AgentOccam and SteP show that higher-level actions and policies help: SteP raised WebArena from 14.9% to about 33–36% with 2.3× smaller context. One caution: in an Online-Mind2Web failure analysis, grounding errors were more likely when several actions ran before the next observation.

**Sources:** https://www.anthropic.com/engineering/writing-tools-for-agents · https://arxiv.org/abs/2310.03720 · https://arxiv.org/pdf/2606.02031

**Apply:**
- `fill_fields({label: value, ...})` fills a whole step and returns a readback of what's actually in the fields.
- `paginate_extract(handle, max_pages)` covers model-selected result sets (allowed by your rules).
- Instruct the agent to issue independent reads in parallel within one turn.
- Batch actions only where you also read back the result.

**Estimate:** 20–35% fewer turns.

## 5. Use JSON from the site's own network calls when it's there

**Summary.** "Beyond Browsing" (CMU): browsing only 14.8%, API only 29.2%, hybrid 38.9% on WebArena (v3). The API advantage shrinks on sites with poor API support. WALT (Salesforce, ICLR 2026) turns UI flows into URL-parameter tools: 50.1% on WebArena and +20.5% over a tool-free baseline on Online-Mind2Web.

**Sources:** https://arxiv.org/abs/2410.16464 · https://proceedings.iclr.cc/paper_files/paper/2026/hash/5b175f9e93873e3a10a6ce43dbb82e05-Abstract-Conference.html

**Apply.** Use a CDP listener that saves JSON/XHR responses for the page the model chose and lists them as another source the model can read. Also let the model edit query parameters (page size, filters) on URLs it has already seen. **Caveat:** SAP-style and webmail mockups are often server-rendered, so this may do nothing on the unseen sites. **Estimate:** large where it applies (one call instead of paging), zero otherwise. It's generic, so it's cheap insurance.

## 6. Reliability: checks in code first, a verifier model only for what code can't check

**Summary.**
- LangExtract maps each extracted value to exact character offsets in the source and reports exact or fuzzy alignment. It has no published accuracy benchmark.
- Surfer-H uses a separate validator. Swapping a weaker model in as validator dropped accuracy by 12–16 points, so validation needs a strong model.
- WorkArena checks results by querying the saved database, not the confirmation screen.
- ClawBench reports common failures: missing required fields, skipped confirmation steps, and mis-clicks on elements with similar labels (secondary summary).
- Self-consistency across runs: the evidence for extraction is weak and depends on the model, and a 2025 abstract argues it has become wasteful with stronger models.

**Sources:** https://developers.googleblog.com/en/introducing-langextract-a-gemini-powered-information-extraction-library/ · https://arxiv.org/abs/2506.02865 · https://arxiv.org/abs/2403.07718 · https://api.emergentmind.com/topics/clawbench

**Apply:**
- Every recorded value must match a substring of its source span. That comes free with #3a.
- Deterministic checks: totals add up, price-scale tiers are monotone, validity dates cover the bid date, revision is the latest.
- Before signing, compare the form against the record store field by field, and re-read the confirmation page.
- Spend extra model calls only on fields flagged as conflicting: two sources disagree, or there are multiple revisions or validity windows. Skip whole-run self-consistency; it roughly doubles cost for little gain at your accuracy level.

## 7. Masking old tool results (useful if you own the conversation loop)

**Summary.** "The Complexity Trap" (JetBrains, NeurIPS 2025 workshop) found that masking old observations with a rolling window of the last 10 roughly halved cost (−51% to −57% across models) with solve rates statistically unchanged. LLM summarization made trajectories longer (52 vs 44 turns) and its summary calls broke caching. The best window depended on the scaffold (10 for SWE-agent, 58 for OpenHands). Anthropic's context editing cut tokens 84% on a 100-turn search eval.

**Sources:** https://arxiv.org/abs/2508.21433 · https://claude.com/blog/context-management

**Caveat for you.** With Anthropic caching, every mask invalidates the cached prefix and rewrites the remainder at 1.25×, which is why the API has a `clear_at_least` threshold. I didn't confirm whether the CLI exposes context editing; in practice it only gets auto-compaction. If you move to your own loop, mask in large batches. Otherwise #1 gets you most of this benefit. Never use LLM summarization here.

## 8. Low priority or overstated

- **Speculative actions** (ICLR 2026 oral): at most 20% lower latency at 55% next-action prediction accuracy, and it costs extra branches. Skip it. https://arxiv.org/abs/2510.04371
- **Code execution / programmatic tool calling:** Anthropic's 98.7% figure is one worked example; the 37% figure (complex research tasks) comes from secondary sources and I couldn't find it on Anthropic's page. It would only help if the model scripted multi-page reads, which risks the "crawler" rule. https://www.anthropic.com/engineering/code-execution-with-mcp
- **Benchmark scores generally:** "An Illusion of Progress" (COLM 2025) found most agents' self-reported WebVoyager scores, including Browser Use and Agent-E-style setups, fall to about 30% under human evaluation on Online-Mind2Web, with Operator at about 61%. Don't copy architectures because of leaderboard numbers. https://arxiv.org/abs/2504.01382
- **Screenshots** helped GPT-4o only very slightly on WorkArena and add about 0.8 s per step in Browser Use. Use the accessibility tree or distilled DOM, with screenshots only when visuals matter.
